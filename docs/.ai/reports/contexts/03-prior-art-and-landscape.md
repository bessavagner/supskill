## Per-tool detail

### 1. BMAD Method / `claude-code-bmad-skills`

Confirmed via its own docs: the plugin **never writes code**. Its four-phase lifecycle (Analysis → Planning → Solutioning → Implementation-handoff) ends at a `bmad-readiness-check` gate that returns PASS/CONCERNS/FAIL, and on PASS emits a `handoff-manifest.json` — story files with owned scopes, wave assignments, dependency lists, and "locked sections" that downstream dev tools must not touch. That manifest is explicitly "tool-agnostic": BMAD's job stops the moment a human or another tool starts writing code. It has a real human gate (the readiness check) but no execution loop at all, so it isn't a competitor to supskill's core claim (driving a backlog through execution) — it's a possible *upstream* stage.

### 2. `prime-radiant-inc/iterative-development` — closest competitor

This is the one to take most seriously. It runs a five-phase loop (requirements extraction → walking skeleton → sprint execution → audited review via "parallel adversarial review" → termination when the roadmap drains) and, critically, **says outright it composes superpowers** rather than inventing new methodology: "This plugin depends conceptually on skills from the superpowers plugin (brainstorming, TDD, parallel adversarial review, verification-before-completion)." That is exactly supskill's stated design principle, already shipped by someone else.

Where it differs from supskill's pitch: no documented human gate. Failed audits "feed gaps back into the backlog" and the loop just keeps going — there's no evidence of a pause-and-ask primitive between sprints, let alone the three-gate cadence supskill proposes (sprint doc, dev plan, post-execution). Its context-management story is also thinner in public docs than Ralph's or flow-next's — it clearly keeps on-disk artifacts (per-epic files, a coverage ledger, a "sentinel corpus") but doesn't document *how* it draws context boundaries between sprints or what happens if the driving session itself dies mid-loop. If supskill's actual differentiator is "gates + survives its own context death," iterative-development's silence on both of those points is the opening — but it's a narrow one, since the core loop mechanics it already has are 80% of the job.

### 3. Ralph Wiggum loop

Origin: Geoffrey Huntley, ghuntley.com/ralph. In its purest form it's `while true; do cat PROMPT.md | claude-code; done` — a completely fresh context window every iteration, with all continuity carried on disk (`fix_plan.md`, `specs/*`, `AGENTS.md`, git history, test output). Two productized descendants exist: Anthropic's own `ralph-loop`/`ralph-wiggum` plugin (a stop-hook that re-feeds the prompt while preserving file state, with `--max-iterations` and a `--completion-promise` string) and `coleam00/ralph-loop-quickstart`, which pointedly brands itself as "the right way — NOT using the Anthropic plugin," pairing the raw bash loop with a `/create-prd` planning step and framing Ralph as **for proof-of-concepts, not production**.

Failure modes the author himself documents (this is the strongest first-party critique in the whole landscape): token burn from re-reading the full spec every loop; total derailment from a single spec defect (a duplicated lexer keyword corrupted a month of output); Claude's bias toward placeholder implementations, requiring adversarial prompt language to suppress; no approval gate before commits; unpredictable cost. His own conclusion: "Anyone claiming that engineers are no longer required and a tool can do 100% of the work without an engineer is peddling horseshit." Ralph is a *primitive* (fresh-context-per-iteration + disk-as-memory), not a competing product — supskill's "compose, don't invent" framing could legitimately use Ralph as its execution-stage primitive rather than treating it as prior art to beat.

### 4. RALF pattern (Read → Act → Loop → Finish)

Not a tool, a vocabulary for the same idea Ralph implements: bound each `Act` to one verifiable objective, write results durably, let `Loop` decide whether to continue. Useful for supskill's own internal naming/pitch (its stages already map cleanly onto Read/state-load, Act/plan-or-execute, Loop/gate-decision, Finish/sprint-close) but there's no reference implementation or opinion on human gating to compare against.

### 5. GitHub spec-kit

`/specify → /plan → /tasks → /implement`, with a persistent `constitution.md` for cross-phase principles and a documented "Phase -1: Pre-Implementation Gates" requiring human sign-off on simplicity/anti-abstraction/integration-first before implementation starts. This is a real, designed human checkpoint — but it's scoped to **one feature at a time**; nothing in the toolkit loops across a backlog of many features, and the project's own framing describes SDD as "assembling existing tools and maintaining discipline," i.e., the user manually re-runs `/specify` for the next feature. It also reinvents its own SDD lifecycle rather than composing an existing skill library. Its main lesson for supskill: a single well-placed pre-implementation gate with explicit named criteria (not just "human reviews an artifact") is a stronger pattern than an implicit review step.

### 6. `barkain/claude-code-workflow-orchestration` and Anthropic agent teams

Barkain's plugin is a hook-based task-decomposition/delegation framework with "soft enforcement" — escalating nudges (silent → hint → warning → strong reminder) rather than hard blocks — across 8 specialized agents, with native Claude Code plan-mode integration. It is not aimed at backlog/sprint cadence at all; it's closer to a within-session delegation policy than a multi-sprint conductor. Anthropic's own "agent teams"/Workflow tooling direction (visible in the containment engineering post, below) is moving toward environmental containment (sandboxes, boundaries) rather than per-step gates — worth noting as a headwind for any design that leans heavily on frequent human gates.

### 7. `obra/superpowers` — the base layer supskill composes

Superpowers already has real human-in-the-loop design: `brainstorming` gates design before planning, `writing-plans` gates plan review before execution, `executing-plans` checkpoints between task batches, and `subagent-driven-development` has a two-stage review (spec compliance, then code quality) between tasks. Context management is implicit — each skill's sequential activation naturally partitions context — but there's no mechanism to clear context *between* skill invocations, and no persistence layer to resume a `writing-plans → executing-plans` handoff if the driving session dies. Crucially, everything is scoped to **one engineering task on one branch**; `finishing-a-development-branch` is the terminal skill, and nothing in the plugin selects the next backlog item or recycles into a new branch automatically. This is the literal gap supskill's own pitch describes filling — confirmed directly from the skill set's own scope boundary, not inferred.

### 8. Other backlog→sprint→execute closed loops found

- **`damienlaine/agentic-sprint`**: Architect → parallel implementer agents → QA → review, capped at 5 iterations, with a real pause-and-ask gate on cap/stall ("adjust specs, continue iterating, or intervene manually"). Its "convergent diffusion" context strategy — stripping completed work out of the spec each round so each iteration only carries what remains — is a genuinely useful pattern for keeping context bounded across an audited loop. Weak point: the gate is a single blunt cap-trigger, not placed at methodology-meaningful boundaries.
- **`sour4bh/claude-loop`**: A straight Ralph-technique plugin (stop-hook re-injection, iteration/idle caps, exploitation/exploration mode switching, scope-reminder repeated each loop to fight drift). No human gate by design ("no completion promise").
- **`gmickel` marketplace's flow-next**: The most architecturally serious competitor after iterative-development. It has an explicitly named, documented gate concept — "consent boundary: humans bless specs, loops drain them" — plus fresh-context "worker" subagents that re-anchor to spec + git state per task (avoiding the token-bleed Ralph suffers from), cross-model review to a SHIP verdict, and a "Ralph autonomous mode" harness for overnight runs. Its weakness relative to supskill's stated principle: it is **not** composed from existing skills — it invents its own six-object handover model (spec → tasks → evidence → PR body → review threads → merge) and ships its own dependency-free CLI (`flowctl`). Adopting flow-next means buying an entire parallel framework, not layering a thin conductor over `superpowers`/`pm-execution`.

## Escalation patterns worth stealing

- **LangGraph `interrupt()` / `Command(resume=...)`**: a node calls `interrupt(payload)`, execution pauses exactly there, state is checkpointed to a persistence layer, and the thread can be resumed — "months later, on a different machine" — by passing a `Command(resume=...)` back in. The advice to be *selective* about interrupt placement ("don't interrupt at every step — this creates bottlenecks... identify the critical decision points where human judgment adds the most value") is a direct answer to the approval-fatigue problem below, and maps well onto supskill's three proposed gates if each is justified as a genuine decision point rather than a checkpoint-for-its-own-sake.
- **Temporal signals + durable timers**: external approval arrives as a `Signal` into a workflow that is durably parked — "interrupted threads don't take up any resources... can be resumed many months later" — with a durable timer bounding how long a human has to respond. The auditability angle ("all decisions, retries, and human approvals are fully auditable" because they're part of replayable workflow history) is worth stealing as a design requirement: every supskill gate decision should leave a durable, replayable record, not just an in-context mention.
- **Anthropic's own shift away from per-action gates** (`anthropic.com/engineering/how-we-contain-claude`): they measured **93% approval rate on permission prompts** and concluded interactive per-action confirmation is "behaviorally unreliable as a sole safety mechanism" once users habituate. Their fix wasn't more/better prompts — it was moving the boundary into the environment (sandboxes, restricted write scopes), which cut permission prompts 84% in Claude Code. Direct quote worth internalizing: "A tight perimeter also means you can relax oversight." This is a real headwind for supskill's thesis (see below) — the platform's own research says fewer, more environmental gates beat more, more frequent human gates.
- **BMAD's PASS/CONCERNS/FAIL readiness check**: a three-valued gate outcome (not just pass/fail) that lets "CONCERNS" proceed with a flagged caveat instead of forcing a binary block — worth adopting instead of a plain boolean gate.
- **Flow-next's "consent boundary"**: gates tied to a concrete artifact state change (spec "blessed," tracker board promoted) rather than a conversational checkpoint — makes the gate machine-checkable, not just a place where the agent happens to pause and ask.
- **Claude Code's deny-first + graduated permission modes** (per `arxiv.org/html/2604.14228v2`): "deny rules always take precedence over allow rules, even when the allow rule is more specific," and denial responses are designed to *shape* the agent's next attempt rather than simply halt it. Useful for how supskill's escalation should read back to the executing agent when a gate blocks it — a redirection, not a dead stop.

## Known failure modes of long autonomous runs (for supskill's "why gates matter" argument)

- **Context rot / context overflow / context drift**: three distinct failure modes documented in the 2026 writeups — overflow (window fills, agent acts on incomplete state), drift (agent still sees recent actions but has lost the original intent/requirements from early in the session), and the "lost in the middle" effect where mid-context information is systematically underweighted regardless of window size.
- **Working-memory rot across multi-agent handoffs**: a degraded context passed from one agent to the next is accepted with "high local confidence" by the receiving agent, so each hop stays locally coherent even as the overall task silently corrupts — no architectural checkpoint catches it because nothing looks wrong at any single hop. This is the concrete mechanism that makes "no gates" (iterative-development, Ralph) risky at scale, and the strongest evidence-based argument for supskill's context-boundary-drawing job.
- **Plan staleness and silent guessing when blocked**: agents facing a blocked/ambiguous step tend to guess plausibly rather than surface the block, and an incorrect belief about system state compounds through every subsequent step built on that faulty premise — documented as coding agents editing further files to "explain away" a type error instead of surfacing it.
- **Observability-evaluation gap** (from the Claude Code architecture paper): "agents tend to respond by confidently praising the work, even when quality is mediocre" — an agent's own self-report is not a reliable completion signal, which is a direct argument for external, human-held gates rather than the agent self-certifying "sprint done."

## The gap supskill fills — and the honest case against building it

**What's actually open**: no existing tool combines all three of (a) explicit composition-only design (no invented methodology — layering `pm-execution:sprint-plan` + `superpowers:writing-plans` + `superpowers:subagent-driven-development`), (b) hard human gates placed at named methodology boundaries (not just an iteration-cap pause), and (c) documented survival of the *conductor's own* context death via on-disk state. iterative-development has (a) and implicitly some of (c), but not (b). Flow-next has (b) and a strong version of (c), but explicitly not (a) — it's its own framework. Superpowers has (b) at the single-task level but none of the backlog-level orchestration. That three-way combination is the real gap, and it's genuinely unoccupied.

**The steelman case against building it:**

1. **iterative-development already does most of the hard part, and is maintained by a team actively shipping in this exact space** (Prime Radiant, with a companion `sprout` project and a public marketplace). Composing `superpowers`, chunking large specs, running audited sprint loops to a drained backlog — that's the expensive part to build and debug, and it already exists, works, and is free. Rebuilding it to add three gate-points risks re-solving a solved problem worse than the incumbent solves it, with a fraction of the field-testing.

2. **The differentiator may be a patch, not a product.** If iterative-development's only real gap is "no pause-and-ask between phases," the fix could be a stop-hook or a thin wrapper skill that intercepts its phase transitions and calls `AskUserQuestion` — plausibly a few hundred lines, not a new plugin with its own identity, docs, and marketplace listing. Before building supskill, it's worth spending a day forking/wrapping iterative-development to see if the gate can be bolted on rather than architected from scratch.

3. **Superpowers' `executing-plans` already has the gate primitive** ("batch execution mode with human checkpoints between task groups") — the ecosystem already contains a working checkpoint mechanism at the task level. Supskil's contribution is *only* lifting that same idea up one level, to the sprint/backlog level. That's real, but it's a smaller leap than the pitch implies once you see the primitive already exists one layer down.

4. **Anthropic's own platform research argues against supskill's central mechanism.** The 93%-rubber-stamp finding and the resulting move toward environmental containment over per-action approval is a direct, first-party signal that *more human gates* is not where the ecosystem is heading — it's where it came from. A three-gate-per-sprint cadence over a long backlog risks reproducing exactly the approval-fatigue pattern Anthropic measured and explicitly designed away from. If gates become a rubber stamp after the fifth sprint, supskill's core claim ("holds human gates") degrades into theater — while providing all the overhead (stopped pipelines, context handoff machinery, a whole plugin surface) of a real gate.

5. **The context-boundary-drawing job — supskill's other stated core job — is what Ralph, iterative-development, and flow-next all already solve**, each with a documented, working answer (fresh-context-per-iteration + disk state; per-epic files + coverage ledger; spec re-anchoring + worker re-reads). Supskil doesn't need to invent a fourth answer to "how do I not run out of context across a long loop" — it needs to pick one of the three existing answers and use it. If the plan is to *design* a novel context-boundary scheme, that re-opens exactly the "don't invent a methodology" promise the whole pitch is built on.

6. **Fast-moving, crowded niche, low differentiation lifetime.** Between BMAD, iterative-development, flow-next, `agentic-sprint`, and `claude-loop`, this exact "backlog → sprint → plan → execute, on a loop" space has at least five actively-updated 2026 entrants. If supskill's edge is "we add gates that they don't have," that edge has a short half-life — iterative-development or flow-next adding an optional gate flag is a much smaller lift for them than building a whole competing conductor is for us, and either could close the gap in a single release.

**Bottom line for the steelman**: the honest recommendation is to prototype the gate-and-context-survival behavior as a *wrapper around iterative-development* (or a documented workflow using flow-next's Ralph mode + its consent-boundary primitive) before committing to a standalone supskill plugin. Build supskill only if that wrapper attempt proves the gate can't be bolted on cleanly — i.e., if the incumbents' architecture actively resists inserting a hard human checkpoint at sprint-doc/dev-plan/post-execution boundaries, which would be the real, validated reason a separate conductor needs to exist.
