## Sprint goal (one line)

> supskill becomes installable and discoverable: the plugin publishes to its own marketplace under the immutable `supskill@supskill` slug with its cross-marketplace dependencies resolving at install time, an eval loop scores the skill description's should-trigger / should-not-trigger discrimination as a pure hit-rate over the description text, and the README plus a build-in-public writeup ship with the escalation finding as the lede — phrased to match the corrected runtime, not the backlog's original wording.

## Why this sprint

Six epics built the conductor; none of them made it something a second person could install. E7 is the packaging seam: `marketplace.json` and `plugin.json` already exist and already name the plugin, but the repo carries no release tag, so no one outside this checkout can run `/supskill` at all. The whole point of the plugin skeleton (E2) and the dependency declarations (invariant 1) is only realised when a `claude plugin install supskill@supskill` actually resolves `superpowers` and `pm-execution` across marketplaces — and that has never been exercised against a published artifact, only asserted by a test (`README.md:142`).

This is the first sprint whose stories are mostly *not* Python and mostly *not* offline-provable. SK-060's publish is an operator-run act; SK-062's writeup is prose judged by a human. Only SK-061 has an offline-amenable core — and only conditionally, since the mechanism it is named after runs live (DoR finding 2) — and even that one carries the sprint's sharpest inherited tension: S2 chose `disable-model-invocation: true` for the conductor because it is side-effecting (`invocation-model.md:1-11`), and recorded in the same file that this exact choice makes SK-061's auto-invocation eval "measure a hypothetical" until E7 decides whether to relax the flag or re-scope the story (`invocation-model.md:13-18`). E7 is where that IOU comes due, and this doc takes the smaller, reversible side of it (see risks).

**Scope boundary, stated up front.** E7 is the first epic in the backlog's recommended build order whose stories are still unchecked. E6 carries two ☐ rows — SK-055 and SK-056 — but those are backlog debt appended after S6's own PAR review, not E6 scope, and they are not pulled here. E8 (validation) comes after E7 in build order and needs real LLM runs, so it is its own invocation (invariant 6, no look-ahead). This sprint commits E7's three rows and nothing else.

### SK-061 — `skill-creator` eval loop · 3 · S · **(3 → 3, no change at pull time — Gate 1 picked the live-composition fork over the offline-proxy default; see below)**

- **As** the author, **I want** a repeatable eval that scores whether the conductor's `description` fires on the prompts it should and stays silent on the ones it should not, **so that** discoverability is measured against a corpus rather than hoped for.
- **proof:** seam=app-level · impact=cross-surface · provable=operator *(Gate 1 decision, 2026-07-15: compose `skill-creator`'s real `run_loop.py`/`run_eval.py` rather than build a bespoke offline proxy. A hit rate is not "a pure function of the description string" — whether a query triggers is a model judgement at runtime — so the honest seam for a real trigger-rate measurement is app-level/operator with a real token budget, not unit/offline. See [DoR finding 2](#dor-findings-refined-at-pull-time) for the fork this decision resolved, and finding 3 for why this does NOT require flipping `disable-model-invocation`)*

- **Context.** `skill-creator` is installed (`claude-plugins-official/skill-creator`) and its Description-Optimization loop (`run_loop.py` → `run_eval.py`, `subprocess.Popen`-driven `claude -p <query>` calls, three runs per query for a trigger rate) is exactly the should-trigger/should-not-trigger mechanism the backlog names. REFINE's DoR finding 3 resolves the tension `invocation-model.md:13-18` flagged: `skill-creator`'s harness registers the skill into `.claude/commands/` to make it model-reachable for the eval, which is a **separate path** from the SKILL.md frontmatter's `disable-model-invocation: true` (`skills/supskill/SKILL.md:5`) — so composing the real loop measures a genuine trigger rate for the shipped `description` (`skills/supskill/SKILL.md:3`) **without** relaxing the conductor's own auto-invocation flag. That flag stays disabled; this decision is scoped to the eval mechanism only, exactly as finding 3 recommended keeping the two calls separate.

- **Accept:**
  - The eval is `skill-creator`'s actual `run_loop.py`/`run_eval.py` composed against a should-trigger / should-not-trigger corpus for the conductor's `description` — not a bespoke proxy scorer.
  - The corpus's should-not-trigger half includes the near-misses that matter for a side-effecting conductor: read-only sprint questions, other-repo sprint tooling, and prompts that name "sprint" without wanting to *run* one.
  - `skills/supskill/SKILL.md`'s own `disable-model-invocation: true` frontmatter is untouched by this story — the command-registration path `skill-creator` uses to make the eval live is separate from that flag (DoR finding 3), and the report states this plainly so the two decisions are never conflated.
  - A real, bounded token budget is set and recorded before the eval runs (this is a live `claude -p` spend, three calls per corpus query); the run is operator-gated, not part of the default offline test suite.
  - `skill-creator` is used at author/eval time only — it must **not** be added to `plugin.json`'s `dependencies` or the `DISPATCHED_SKILL_PLUGINS` manifest-test set (DoR finding 6); the conductor never dispatches it at runtime.
  - The report states plainly that the hit rate measures a real trigger rate for a command-registered copy of the description (DoR finding 3's framing) — a fair proxy for auto-invoke behaviour if the flag were ever relaxed, not identical to it.

## DoR findings (refined at pull time)

Seventh sprint refined against live source. Sprint stays **9 → 9 pts** (SK-060 3 → 3, SK-061 3 → 3, SK-062 3 → 3) — the first REFINE pass in this backlog that did **not** grow points, and that is itself a finding worth stating plainly: E7's stories are mostly not-Python and mostly not-offline-provable, so the sharpest things this pass found are not missing plumbing to build (the shape S1–S6 kept finding) but **claims in the SCOPE draft that the live world contradicts** — a repo already public, an "offline" eval whose named mechanism is live, a tag that resolves nothing. Correcting a claim is not the same as adding scope; the honest delta is 0 points and six corrections. Where this pass had to make a call the draft did not settle, it took the smaller, reversible default and left the fork to Gate 1.

**Citations verified.** Every backtick `path:line` citation in this doc resolves against the working tree (`supskill-audit` passes; the resolver matches by path suffix, so bare `plugin.json:2` resolves against `.claude-plugin/plugin.json` — `scripts/supskill_state/citations.py:63-64`). One **existing** defect from the SCOPE pass was fixed in this one: SK-062's proof line read `seam=doc`, which is not a grammar token — `proofs.py` accepts only `unit|integration|app-level|e2e` — so `--proofs` failed the doc until it was corrected to `seam=app-level`.

1. **The repo is already public — SK-060's "make it public" half is a verify, not a do.** The SCOPE draft's accept criteria named "the GitHub repo … is public" as an act to perform, but `gh repo view bessavagner/supskill` already reports `"visibility":"PUBLIC"` at pull time. What genuinely remains unwalked is narrower than the draft framed it: `claude plugin marketplace add` + `install` from a clean environment, and the cross-marketplace resolution underneath. `git tag` is still empty (verified), so no release has ever been cut — but see finding 4 for what the tag does and does not buy. Recorded so nobody spends a step re-doing a done thing. **No point change.**

2. **The mechanism the story names — `skill-creator` — is a live `claude -p` loop, not offline; SK-061's `provable=offline` and "no LLM in the harness" cannot both hold with it.** `skill-creator` exists and is installed under `claude-plugins-official` (its `SKILL.md` at `~/.claude/plugins/marketplaces/claude-plugins-official/plugins/skill-creator/skills/skill-creator/`; these are external plugin files, outside this repo's tree, so they carry no audit-resolvable `path:line` — verified by direct read, not cited as an in-tree line). Its Description-Optimization loop is exactly the should-trigger/should-not-trigger mechanism the backlog names — but that loop is `python -m scripts.run_loop`, which drives `run_eval.py`, and `run_eval.py` shells out to `claude -p <query>` via `subprocess.Popen`, running each query three times for a trigger rate. That is a live model spend per query, not a pure function. The deeper problem the draft glossed: a hit rate **cannot** be "a pure function of the description string" (SK-061's own proof parenthetical, pre-correction) — whether a query triggers is a model judgement at runtime; any purely offline number is a lexical/semantic *proxy*, not a prediction of live triggering. **Recommended answer (the Gate 1 fork):** (a) keep the flag disabled and build a bespoke **deterministic proxy** scorer over an authored corpus — honestly offline, `provable=offline`, but state plainly it is a proxy that does not predict live triggering and is **not** `skill-creator`'s loop; or (b) compose `skill-creator`'s real `run_loop.py` (invariant 1, compose-never-reinvent), accept `provable=operator` and a real-token budget, and treat the corpus as the offline artifact while the scorer is operator-run. The smaller, reversible default this doc carries is (a); the corpus is offline either way, so the story's size does not move. **No point change** — but if the operator picks (b) at Gate 1, re-point for the live-run harness wiring and a token budget.

3. **`skill-creator`'s harness sidesteps `disable-model-invocation: true` by registering the skill as a command — so "the eval measures a hypothetical while the flag stands" is only half right.** Its `run_eval.py` (external, path in finding 2) writes the skill into `.claude/commands/` so it appears in Claude's `available_skills` list, then invokes it; that path is model-reachable regardless of the SKILL.md frontmatter flag (`skills/supskill/SKILL.md:5`). So `skill-creator`'s loop would measure a **real** trigger rate for a command-registered copy of the shipped `description` (`skills/supskill/SKILL.md:3`) — a fair proxy for what auto-invoke would do if the flag were relaxed — not a literal reading of the disabled auto-invoke path, and still real tokens. This tightens the `invocation-model.md:13-18` tension rather than resolving it: the draft's "keep the flag, score offline" default is coherent **only** under finding 2's option (a); option (b) does not need the flag flipped at all, because the command-registration path never consulted it. Recorded so the flag decision and the offline decision are not conflated — they are two separate calls. **No point change.**

4. **The `v0.1.0` tag is release hygiene, not an install-resolution requirement.** The SCOPE draft coupled "a `v0.1.0` release/tag is cut" to "install succeeds," implying the tag is load-bearing. It is not: the marketplace's own plugin entry is `"source": "./"` with no version pin (`.claude-plugin/marketplace.json:12`), so `claude plugin marketplace add` resolves it at the repo's default branch, not a tag. Claude Code's `{plugin}--v{version}` tag convention governs **dependency version constraints**, and supskill pins none — deliberately, because neither upstream marketplace tags releases that way, and a constraint with no matching tag would *disable* supskill (`tests/test_plugin_manifest.py:126-136`, the live guard that fails the suite if any dependency gains a `version`). So `claude plugin install supskill@supskill` succeeds with or without a `v0.1.0` tag. Recommendation: keep the tag as a GitHub release marker (release notes reference the finding, per the fourth accept bullet), but do not gate the "install succeeds" acceptance on it, and do **not** add version pins to the two dependencies while resolving SK-060. **No point change.**

5. **`README.md:142`'s "a test asserts …" is declaration + allowlist, not resolution — which is exactly why SK-060's real install is the only proof.** The two live tests are `test_every_dispatched_skill_has_its_plugin_declared_as_a_dependency` (`tests/test_plugin_manifest.py:98`) — every `superpowers:`/`pm-execution:` namespace the conductor's prompts dispatch has its plugin in `plugin.json` `dependencies` — and `test_cross_marketplace_dependencies_are_allowlisted` (`tests/test_plugin_manifest.py:113`) — every declared cross-marketplace dep is in `allowCrossMarketplaceDependenciesOn` (`.claude-plugin/marketplace.json:8`). Neither asserts that install **fetches and resolves** those deps from a clean environment; that is the fact SK-060 must establish for the first time. The doc's risk row and Context already read this correctly ("an assertion, not a fact"); this finding just pins the citation to the two functions so a reviewer can see precisely what the test does and does not cover. **No point change.**

6. **`skill-creator` is an author-time tool, not a conductor-dispatched skill — it must stay out of `plugin.json` dependencies.** SK-061 uses `skill-creator` at authoring time to build/score the eval; the conductor never dispatches it at runtime. `plugin.json`'s `dependencies` are runtime composition — `superpowers` and `pm-execution` only (`.claude-plugin/plugin.json:10-13`) — and `DISPATCHED_SKILL_PLUGINS` in the manifest test is the closed set of skills the conductor's prompts actually invoke (`tests/test_plugin_manifest.py:71-74`). Adding `skill-creator` to either would make the declaration test demand a manifest entry for a tool no stage dispatches, and would pull a third cross-marketplace dep into the install path for no runtime reason. Recorded so SK-061 does not "helpfully" declare it. **No point change.**

**Deliberately NOT in scope**, though tempting: flipping `disable-model-invocation` (finding 3 keeps it a separate, operator-owned call, not a packaging default); pinning dependency versions (finding 4 — the live guard at `tests/test_plugin_manifest.py:126-136` exists precisely to stop this); E8's validation (invariant 6, its own invocation); E6's SK-055/SK-056 backlog debt (excluded by the dispatch); and any attempt to make SK-061's offline number *claim* to predict live triggering (finding 2 — an offline scorer is a proxy, and the report must say so).
